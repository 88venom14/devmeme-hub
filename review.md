# Code Review — devmeme-hub

Дата: 2026-06-09
Охват: Go backend (`backend/`), React/Vite фронтенд (`src/`), Cloudflare Workers (`auth-worker/`, `chat-worker/`), устаревший Express-сервер (`server/`), деплой (`deploy.mjs`, `.github/workflows`), SQL-схема и миграции.

Легенда серьёзности: 🔴 критично · 🟠 серьёзно · 🟡 средне · 🔵 мелочь/улучшение.

## 1. Безопасность

### 🔴 1.1. Реальные секреты закоммичены/лежат в рабочем дереве (`.env`, `backend/.env`)
`.env` в корне содержал боевые значения (anon-ключ BaaS, URL воркеров). Хотя `.gitignore` исключает `.env`, файл физически присутствует и легко утекает (бэкапы, шаринг, IDE-синк). `backend/.env.example` содержит `JWT_SECRET=change-this-to-at-least-32-characters` — этот плейсхолдер проходит проверку длины (>=32) в `config.Load()`, поэтому при невнимательном деплое прод запустился бы с публично известным секретом подписи JWT → подделка любых токенов.
- Статус: плейсхолдер `JWT_SECRET` теперь отклоняется на старте (`config.Load`); `.env` вычищен от секретов сторонних сервисов. Остаётся: ротировать все секреты воркеров и убедиться, что `.env`/`backend/.env` никогда не были в истории git (`git log --all -- .env`).

### 🔴 1.2. CORS воркеров: `Access-Control-Allow-Origin: *`
И `chat-worker/src/index.ts`, и `auth-worker/src/index.ts` отдают `'Access-Control-Allow-Origin': '*'`. Для chat-воркера это значит, что любой сайт может расходовать ваш OpenRouter-ключ через прокси (ключ скрыт на сервере, но эндпоинт открыт всем и без аутентификации — см. 1.3). Для auth-воркера wildcard в сочетании с OAuth-редиректами — потенциальный вектор.
- Действие: ограничить `Allow-Origin` доменом `https://fluttershy.horsefucker.ru` (и localhost для dev).

### 🔴 1.3. Chat-воркер полностью открыт и без рейт-лимита
`chat-worker` принимает любой POST с `history` и проксирует в OpenRouter под вашим ключом. Нет аутентификации (JWT бэкенда не проверяется), нет ограничения частоты, нет проверки origin. Это открытый платный прокси к LLM — любой может слить ваш биллинг/квоту OpenRouter.
- Действие: требовать Bearer-токен бэкенда (или общий секрет), добавить rate limiting (Cloudflare Rate Limiting / KV-счётчик), ограничить размер `content`.

### 🟠 1.4. Загрузка медиа — нет проверки реального содержимого файла
`media_handlers.go` доверяет `Content-Type` из multipart-заголовка, который контролирует клиент. Можно загрузить произвольный файл (например HTML/JS), указав `image/png`. Файлы потом раздаются через `http.FileServer` с того же origin. Хотя расширение берётся из имени и тип проверяется по белому списку, фактическое содержимое не валидируется (нет sniffing'а через `http.DetectContentType`).
- Действие: читать первые 512 байт и сверять с `http.DetectContentType`; отдавать медиа с `Content-Disposition: attachment` или с отдельного домена; ставить `X-Content-Type-Options: nosniff`.

### 🟠 1.5. Нет ограничения размера отдельного файла / общий лимит = 64 МБ на тело
`MaxRequestBytes` по умолчанию `64<<20` (64 МБ) применяется и к JSON, и к multipart. UI обещает «макс. 50 МБ», но бэкенд этого не enforce'ит для медиа отдельно, а `ParseMultipartForm(s.cfg.MaxRequestBytes)` держит до 64 МБ в памяти/во временных файлах. Возможен DoS заливкой больших файлов.
- Действие: задать отдельный, меньший лимит для медиа; для JSON-эндпоинтов — свой малый лимит.

### 🟠 1.6. JWT без issuer/audience и без механизма отзыва
`auth/jwt.go` выдаёт HS256-токен с TTL 24h, но не проверяет `iss`/`aud`, нет refresh-токенов и нет revocation. Схема (`user_sessions`) под refresh-токены заведена, но не используется. При утечке токена отозвать его нельзя 24 часа; смена пароля не инвалидирует активные сессии.
- Действие: добавить `iss`/`aud` и проверку, рассмотреть короткий access + refresh с хранением хешей в `user_sessions`.

### 🟡 1.7. Brute-force логина не ограничивается
Схема `users` содержит `failed_login_attempts` и `locked_until`, но `login()` их не использует и не инкрементирует. Нет rate-limit на `/api/auth/login`. Возможен перебор паролей.
- Действие: реализовать счётчик попыток/блокировку либо rate-limit по IP.

### 🟡 1.8. Регистрация сразу `status='active'` без подтверждения email
`register()` ставит `email_verified_at = NOW()` и `status='active'` без какой-либо верификации. Любой email можно «занять».
- Действие: при необходимости — flow подтверждения email; как минимум осознанно задокументировать.

### 🟡 1.9. `X-Forwarded-Proto` принимается без доверенного прокси
`media_handlers.go::scheme()` берёт `X-Forwarded-Proto` от клиента напрямую. Если фронтящего reverse-proxy нет/он не очищает заголовок, клиент может подменить scheme в сформированном URL медиа.
- Действие: доверять заголовку только от известного прокси (или брать scheme из конфигурации base URL).

## 2. Корректность / баги

### 🔴 2.1. Go-бэкенд не закоммичен ни в одну ветку
`backend/` присутствует только как untracked в `gh-pages` (`git status` → `?? backend/`) и отсутствует в `main` (`git ls-tree main` его не содержит). При этом фронтенд по умолчанию ходит на `https://api.fluttershy.horsefucker.ru` (Go API). Весь серверный код существует лишь локально — потеря машины = потеря бэкенда; CI его не собирает и не тестирует.
- Действие: закоммитить `backend/` в `main`, настроить отдельный pipeline (`go vet`, `go test ./...`, build).

### 🟠 2.2. `updateMyProfile` не может очищать поля (COALESCE-ловушка)
`profile_handlers.go`: `SET bio = COALESCE($5, bio), ...`. Фронтенд (`SettingsPage`) при очистке поля шлёт `null` (`display_name: ... || null`, `avatar_url`, `banner_url` через кнопку «удалить»). COALESCE с NULL означает «оставить старое значение» — то есть **пользователь не может удалить аватар/баннер/био/ссылки**, изменение молча игнорируется. Это рассинхрон контракта фронт↔бэк.
- Действие: использовать паттерн «поле присутствует в JSON → обновить», например через `*sql.Null*`/отдельные флаги или `jsonb`-merge; либо различать «не передано» и «передано null» (сейчас `decodeJSON` с `DisallowUnknownFields` этого не различает для `*string`).

### 🟠 2.3. Дублирующиеся/устаревшие реализации бэкенда сосуществуют
В репозитории сосуществовали три «бэкенда»: Go API (`backend/`), мёртвый Express-сервер (`server/index.ts`) и Cloudflare auth-воркер. Фронтенд использует собственный JWT Go-API (`src/lib/api.ts`). Это был мёртвый и противоречивый код.
- Статус: РЕШЕНО. `server/` и auth-воркер удалены, единственный бэкенд — Go API. Весь устаревший legacy-код стороннего BaaS вычищен из проекта.

### 🟠 2.4. OAuth-вход не работает с текущим бэкендом
`LoginPage.handleOAuth` просто показывает «OAuth пока не подключён к локальному backend». Сессия в приложении — это Go-JWT в localStorage (`devmeme_token`). Удалённый auth-воркер был несовместим с этой архитектурой. OAuth-кнопки остаются заглушкой до реализации OAuth на стороне Go (таблица `auth_identities` для этого уже есть).
- Действие: либо реализовать OAuth на Go-бэкенде (таблицы `auth_identities` уже есть), либо убрать нерабочие кнопки.

### 🟡 2.5. `useChat`: история для LLM собирается до вставки и без учёта гонок
`useSendMessage`: читает историю, добавляет реплику локально, потом отдельным запросом вставляет user-сообщение, инвалидирует кэш, зовёт LLM, вставляет ответ. Между «прочитал историю» и «вставил» нет транзакции; при параллельных отправках возможны рассинхроны/дубликаты. Также если вставка assistant-ответа упадёт после успешного LLM-вызова, ответ теряется, но в UI уже мог мелькнуть.
- Действие: вставлять user-сообщение и возвращать историю одним запросом; ответ ассистента писать идемпотентно.

### 🟡 2.6. `comments.parent_id` не проверяется на принадлежность тому же посту (на уровне API)
`createComment` принимает `parent_id` и `post_id` от клиента и вставляет напрямую. Целостность держится только на составном FK `comments_parent_same_post_fk` в схеме (хорошо, что он есть). Но ошибку FK API возвращает как `500 could not create comment`, а не как осмысленный 400.
- Действие: при нарушении FK/констрейнтов отдавать 400 с понятным сообщением (как сделано для unique violation).

### 🟡 2.7. Лимиты валидации рассинхронизированы между слоями
- Фронт `validation.ts`: `content` max 8000, `password.min` = 6.
- Go `createPost`: контент вообще не ограничивается по длине в коде (полагается на CHECK).
- SQL `001_init`: `content_md <= 20000`, но миграция `003` **удаляет** `posts_content_md_length` → лимита в БД больше нет.
- `server/index.ts` (мёртвый): content max 2000.
- Регистрация на Go требует пароль >= 8, а фронт разрешает от 6 → юзер вводит 6–7 символов, проходит фронт-валидацию и получает 400 с бэка.
- Действие: свести лимиты в один источник; согласовать минимальную длину пароля (6 vs 8).

### 🟡 2.8. `limitParam` использует `fmt.Sscanf` и парсит «12abc» как 12
`Sscanf("%d")` для `?limit=12abc` вернёт 12 без ошибки. Не баг безопасности (есть `maxLimit`), но небрежно.
- Действие: `strconv.Atoi` с явной проверкой.

### 🔵 2.9. `uploadPostMedia(file, userId)` игнорирует `userId` (`void userId`)
`src/lib/storage.ts` принимает `userId`, но не использует — мёртвый параметр (userID берётся из токена на бэке). Лучше убрать из сигнатуры.

## 3. Деплой / конфигурация

### 🟠 3.1. Хрупкий деплой через `deploy.mjs` со «стаб»-костылём CSS
`deploy.mjs` вручную создаёт пустой `assets/index2.css`, потому что Vite ссылается на несуществующий CSS-чанк. Это симптом проблемы конфигурации сборки, а не решение. Кроме того скрипт коммитит **всё** (`git add -A`) на `gh-pages`, мешая исходники, `dist/` и `assets/` в одной ветке — отсюда огромный «грязный» `git status`.
- Действие: разобраться с пустым CSS-чанком (вероятно из-за `rehype-highlight` side-effect import); не коммитить артефакты сборки в ветку с исходниками; хранить только `dist/` для Pages.

### 🟠 3.2. Два механизма деплоя противоречат друг другу
Есть GitHub Actions workflow (`deploy.yml`, билдит из `main`, публикует `dist/` через `actions/deploy-pages`) **и** ручной `deploy.mjs` (коммитит в `gh-pages`, пушит CNAME). Они используют разные модели публикации Pages (artifact vs branch). Параллельное использование приведёт к конфликтам/непредсказуемому состоянию Pages.
- Действие: выбрать один путь. Рекомендуется Actions из `main`, удалить `deploy.mjs`-публикацию.

### 🟡 3.3. `dist/` и `assets/` закоммичены в `gh-pages`
Сборочные артефакты в git раздувают репозиторий и создают шум в диффах (видно в стартовом `git status`: десятки `M dist/assets/*.js`).
- Действие: не версионировать билд; полагаться на Actions-artifact.

### 🟡 3.4. `compatibility_date = "2025-01-01"` у воркеров уже устарела
Не баг, но стоит обновить к актуальной дате для корректного поведения runtime.

## 4. Качество кода / поддерживаемость

### 🟡 4.1. Инлайн-стили повсюду, нет дизайн-системы компонентов
Огромные объекты `style={{...}}` в каждом компоненте (`CreatePostPage`, `VideoPlayer` и т.д.), дублирование hover-логики через `onMouseEnter/Leave`. Тяжело поддерживать и нет переиспользования.
- Действие: вынести в CSS-модули/utility-классы или хотя бы общие style-объекты; hover — через CSS `:hover`.

### 🟡 4.2. Нет тестов ни на одном слое
`go test ./...` — тестов нет; фронтенд-раннер не настроен (сказано прямо в AGENTS.md). Для auth/JWT/медиа-загрузки и SQL-хелперов отсутствие тестов рискованно.
- Действие: добавить unit-тесты на `auth`, `httpapi` (через httptest), `validation.ts`, `tags.ts`.

### 🟡 4.3. `chat-worker` — `sanitizeReply` хрупкая эвристика
Регэксп-чистка `<think>` и «осиротевших» первых строк (`< 12 символов`) может резать легитимный контент (например короткое первое слово ответа). Это запах: модель/промпт «протекают», а лечится постобработкой.
- Действие: по возможности отключить reasoning на стороне модели/параметров запроса, а не вырезать regex'ом.

### 🔵 4.4. Системный промпт чата захардкожен в воркере
Большой русскоязычный промпт-персонаж зашит в `chat-worker`. Это нормально для пет-проекта, но не конфигурируемо и раздувает воркер.

### 🔵 4.5. Логи в репозитории
`backend/api.log`, `backend/api.err.log`, корневые `vite.log`, `vite.err.log` присутствуют (хоть и в .gitignore как `*.log`). Стоит удалить из рабочего дерева.

### 🔵 4.6. `media/` с реальным загруженным файлом лежит в рабочем дереве
`backend/media/0b04e0bb-.../*.jpg` — пользовательский контент в репозитории разработки. В .gitignore он есть, но физически присутствует.

### 🔵 4.7. `App.tsx`: смешанные top-level `import` и `React.lazy`
`AppShell` импортируется обычным образом ниже блока `lazy`-импортов и ниже CSS-импортов — работает, но стилистически вперемешку. Мелочь.

## 5. Схема БД / данные

### 🟡 5.1. Миграция 003 необратимо ослабляет валидацию
`003_relax_legacy_content_constraints.up.sql` дропает `profiles_username_format`, `tags_name_format`, `posts_content_md_length`. После этого:
- длина `content_md` ничем не ограничена в БД (а в коде Go тоже не ограничена) → можно сохранить мегабайтные посты (в пределах 64 МБ тела);
- формат username/tag не проверяется в БД — остаётся только клиентская/недостаточная серверная валидация (Go-`createPost` приводит тег к lower и фильтрует пустые, но не проверяет regex).
- Действие: либо вернуть разумные CHECK'и (с учётом легаси-данных), либо явно перенести валидацию в Go и задокументировать.

### 🔵 5.2. `search` по `ILIKE '%q%'` без индексов
Поиск постов/профилей использует `ILIKE '%...%'` — не использует B-tree индексы, будет медленным на росте данных.
- Действие: при росте — `pg_trgm` GIN-индексы или полнотекстовый поиск.

### 🔵 5.3. Подсчёты звёзд/комментариев коррелированными подзапросами
В каждом списке постов `star_count`/`comment_count` считаются скалярными подзапросами на строку, а trending дополнительно сортирует по тем же подзапросам. На больших объёмах — N×2 подзапросов.
- Действие: при необходимости — материализованные счётчики или `LEFT JOIN ... GROUP BY`.
